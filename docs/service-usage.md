# Encrypted service Usage sidecar — protocol 1

This is a separate resource on the same HTTPS origin as encrypted V1 sync. The existing V1 capabilities, vault, snapshot and receipt response shapes and limits do not change. An old client can continue to restore and replace its V1 settings/history snapshot without seeing or touching Usage. V1 `activity` (`sourceDeviceId` / date / `count`, `chars`, `durationMs`) is not service Usage. Do not place unsupported values (including Beta `pipelineMode=deepseek`) into a V1 snapshot; legacy-safe preferences are a client responsibility. `voiceActivationHotkeyLinked` is device-local.

## Discovery, requests and recovery

| Method and path | Request | Success |
| --- | --- | --- |
| `GET /v1/features/service-usage` | Public, no credentials or redirect | Exactly `{"protocolVersion":1,"maxCiphertextBytes":1048592,"maxBodyBytes":1572864}` |
| `GET /v1/me/vault/usage` | Sync bearer; optional Usage `If-None-Match` | `UsageMetadata` and `ETag`, or `304` and `ETag` with no body |
| `GET /v1/me/vault/usage/snapshot` | Sync bearer; Usage `If-Match` | `UsageSnapshot` and the matching `ETag` |
| `PUT /v1/me/vault/usage/snapshot` | Sync bearer; Usage `If-Match`; `Idempotency-Key`; `UsageSnapshot` | `UsageReceipt` and `Idempotency-Replayed: true\|false` |
| `GET /v1/me/vault/usage/operations/{operationId}` | Sync bearer; UUIDv4 path | `UsageReceipt` |
| `PUT /v1/me/vault/usage/password-change` | Sync bearer; **V1 vault** `If-Match`; `Idempotency-Key`; `UsageRotationRequest` | `{"vaultReceipt":<V1 OperationReceipt>,"usageReceipt":<UsageReceipt>}` and `Idempotency-Replayed: true\|false` |

`GET` uses an empty request body. `PUT` uses `application/json` without compression. JSON objects are strict: unknown or duplicate fields are not accepted on upload. Interpret only a validated same-origin feature `200` as support, or the legacy service's expected same-origin `404 invalid_request` error envelope as unsupported; TLS, transport, redirect, auth, throttling or malformed responses must be distinguishable from unsupported. Never probe or fall back to a legacy plaintext endpoint. The feature probe describes protocol support, not consent or permission to write.

`UsageMetadata` has exactly `protocolVersion:1`, `state:"empty"|"active"`, `ownerGithubId` (canonical positive decimal string), `vaultId` and `keyId` (canonical lower-case UUIDv4), `revision` (canonical uint64 decimal string), `updatedAt` (UTC timestamp), `lastOperationId` (UUIDv4), `ciphertextSha256` (lower-case hex SHA-256), and `ciphertextBytes` (integer). Active means positive revision, all three optional values populated, and at least 65,552 ciphertext bytes. Empty inside an active V1 vault has revision `"0"`, those three values are `null`, and `ciphertextBytes:0`. There is no Usage metadata for an absent or deleted vault. The strong Usage tag matches exactly `^"usage-v1-[0-9a-f]{64}"$` (quotes included); treat it as opaque. It binds both numeric owner and vault/key IDs even when empty. It is distinct from the V1 tag. Wildcards, lists, weak and wrong-namespace Usage tags are invalid.

The strict `UsageSnapshot` has exactly `protocolVersion:1`, `payloadSchemaVersion:1`, `ownerGithubId`, `vaultId`, `keyId`, `baseRevision`, `revision`, `operationId`, `aead:"xchacha20poly1305-ietf"`, `codec:"json-pad64k-v1"`, `nonce`, `ciphertextSha256` and `ciphertext`. The `operationId` uses the same UUID grammar as the V1 protocol. `revision = baseRevision + 1` with no wrap; the server compares **both** the fetched Usage ETag and base revision. V1 and Usage revisions advance independently on ordinary writes. New Usage after vault recreation begins at `"0"` with a different vault/epoch/ETag; do not automatically re-upload a deleted vault's imported records to a new vault. A password change in an empty Usage epoch retains revision `"0"` and changes its ETag.

The exact `UsageReceipt` is `{"operationId":<UUIDv4>,"status":"committed","kind":"snapshot"|"password_change","committedRevision":<positive decimal string>,"committedAt":<UTC timestamp>,"vaultId":<UUIDv4>,"ciphertextSha256":<lower-case hex>}`. A receipt is an immutable commitment, not evidence that those bytes are still the active snapshot. Receipts, with only the hash and no ciphertext, are retained for 604,800 seconds even after rotation or delete. A numeric account's operation IDs are shared across route families during retention: reusing an ID with a different path, method, `If-Match`, or body bytes is `409 idempotency_key_reused`. Exact same-route replay precedes CAS and returns the original receipt without advancing a revision. Usage-only operations are available only in the Usage lookup; V1-only operations only in the V1 lookup; dual rotation appears in both. Client retries must retain the original request bytes, preconditions and ID until the outcome is confirmed. After receipt expiry, re-read and authenticate current state before deciding whether a new write is needed; never blindly replay an expired operation.

Absent/deleted vaults produce `404 vault_empty`/`vault_deleted` on Usage reads and `409 vault_empty`/`vault_deleted` for new writes. A valid snapshot read at an empty Usage head is `404 usage_empty`; a dual rotation on an empty Usage head is `409 usage_empty`. Stale CAS is `412 revision_conflict`; a valid write to the current vault from a stale key is `409 key_epoch_changed`. Error `currentRevision` is that of the resource whose precondition failed (for the dual route, V1 validation/CAS is evaluated before Usage CAS; callers should re-read both on conflict). Authentication, size, malformed-input, media-type, precondition, rate-limit and service errors keep the V1 conventions. A failed write never authorizes overwriting local data. No endpoint exposes record counts, types or any plaintext content.

## Key epochs, rotation and deletion

An old V1 password change is unchanged if no Usage snapshot exists. If one exists, a valid V1-only rotation returns the existing `409 key_epoch_changed` without changing either resource; do not tell the user the password has changed. Upgrade the client rather than deleting or retaining the old cloud key. The upgraded client downloads/authenticates both heads, decrypts both using the current key, makes a fresh V1 `password_change` with new key ID and salt, and re-encrypts the Usage records with that new vault key. The dual request is exactly `{"vaultSnapshot":<V1 password_change SnapshotUpload>,"usageIfMatch":<old Usage strong ETag>,"usageSnapshot":<UsageSnapshot under the new key ID>}`. The snapshots and `Idempotency-Key` share the same operation ID; the owner, vault and new key match; the two nonces must differ. The committed Usage revision advances by one; it does not reset on rotation within a vault. Both replacements, both nonce reservations and both receipts are atomic. After lost acknowledgement, retain both protected key states, check the receipt endpoints or retry the identical dual request, then authenticate current metadata. A competing V1 or Usage write makes the rotation fail without consuming key, salt, nonce or operation ID. When Usage is empty the upgraded client uses the original V1 password-change route; if a first Usage write wins the race the guard requires re-reading both.

A legacy DELETE of a vault atomically removes **both** snapshots when the V1 CAS succeeds. Another device must not apply a stale Usage response from a previous vault/key, upload to a different account, or recreate a vault without explicit user action. A client deleting a vault should clear or quarantine imported records associated with that vault only after resolving the operation; local-origin records remain distinct. Backups remain subject to the service's deletion retention policy.

## Cryptography and bounds

Use the V1-derived 32-byte vault key of the matching key epoch, the same V1 KDF parameters, CSPRNG and framing: `uint32_be(jsonByteLength) || UTF-8 JSON || random padding` to a multiple of 65,536 bytes with at least one block. Use an independent fresh 24-byte XChaCha20-Poly1305 nonce for **every** fresh encryption, including settings/Usage and after rejected writes; the server also reserves nonces across both resources for a numeric owner/key. Do not re-encrypt on exact retry. Use canonical base64url without `=` for nonce and combined ciphertext (last 16 bytes are the AEAD tag); hash the decoded combined ciphertext, not plaintext. The maximum ciphertext is 1,048,592 bytes (16 blocks plus tag), maximum plaintext JSON is 1,048,572 bytes, and standalone Usage PUT is at most 1,572,864 HTTP body bytes. Dual rotation's whole wrapper uses the unchanged 25,165,824-byte V1 HTTP ceiling, enough for both maximal ciphertexts in canonical envelopes. Never put a password, key, plaintext hash or record metadata in the HTTP envelope or logs.

AAD bytes are compact UTF-8 JSON of this ordered array (no spaces, BOM or terminal newline):

```json
["openless-cloud-sync",1,"service-usage","OWNER_GITHUB_ID","VAULT_ID","KEY_ID","BASE_REVISION","REVISION","OPERATION_ID",1,"xchacha20poly1305-ietf","json-pad64k-v1"]
```

Positions 2 and 10 (one-based) are `protocolVersion` and `payloadSchemaVersion`. Use the canonical ASCII wire strings for IDs/revisions. The raw decoded nonce is the AEAD nonce, not part of the array. Independently validate the numeric owner, origin binding, vault, key, revision and metadata hash against the authenticated request and persisted high-water state. A 200/304 response is not proof of valid decryption or of freshness to a brand-new device. The different AAD domain prevents substituting a V1 snapshot for Usage even under the same key. See the [fixed public test vector](../tests/vectors/service-usage-v1.json).

## Encrypted payload and client release gates

The plaintext document is `{ "version": 1, "records": [...] }`. Each record has `id` (stable operation UUIDv4), `occurredAtMs` (i64 UTC Unix milliseconds), `kind` (`asr|llm|tts|multimodal`), `purpose` (`dictation|dictationPostprocess|translation|question|selection|quickNote|voiceEdit|cloudNote|other`), `outcome` (`succeeded|failed|cancelled|unknown`), optional sanitized categorical labels `provider`, `service`, `protocol`, `channel`, `model`, optional `inputAccounting` (`inclusive|excludesCache`), and optional u64 `audioMs`, `inputTokens`, `outputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `reasoningTokens`, `synthesizedCharacters`. Do not put prompts, transcripts, audio, URLs, credentials, headers, or raw provider responses in Usage. Optional fields may be null or absent; compare typed records after normalization. Preserve provider-reported quantities; absent values do not equal observed zeros. Counts and totals are projections, never uploadable operations. These plaintext fields are enforced by clients, not the opaque server.

Keep imported records bound to service origin, numeric owner and vault and separate from locally attributed records. Union by stable UUID; identical duplicates are a no-op; different records for the same UUID fail visibly and preserve both inputs for recovery rather than choosing silently. On CAS conflict download, verify and merge before attempting a fresh write. Compare the canonical merged set to the authenticated remote set **before** re-encrypting; equal sets do not upload. Retain the current encrypted snapshot until an authorized replacement/delete. There is no server-side record TTL or per-record eviction. Initially do not silently window the union or imply a partial projection is complete. If the proposed authenticated set exceeds the client bounds (10,000 records, 8 MiB local input) or the smaller cloud envelope, leave the last valid remote snapshot and the unsynced local records intact and display overflow/unsynced state. Any retention revision is a separate product decision that must account for independent devices returning online and prove that pruned records do not reappear unexpectedly.

Client consent and Usage transport default off; a working feature probe is not consent. No deployment or production enablement before a separate authorized staging target, actual pinned old/new client run, durable restore, explicit history/privacy/consent verification and representative-capacity assessment. The synthetic HTTP/interop tests do not validate shipped UI, production deployment, or those independent gates. For operations and rollback, see [deployment](deployment.md).
